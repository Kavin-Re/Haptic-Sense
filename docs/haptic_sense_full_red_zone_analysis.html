The STM32N6 is NOT like an STM32F4. It has ARM TrustZone and a mandatory First Stage Boot Loader (FSBL). Your application runs from external XSPI RAM, not internal flash. Your current plan and ROADMAP have zero mention of this. A developer unfamiliar with this will spend 3–5 days on first boot alone thinking the hardware is faulty.

Critical < 1 ms preemption is a hard real-time constraint, not a milestone to verify in Week 10
The plan treats < 1 ms preemption as something to "certify" in Week 10 via hardware timers. But preemption latency is baked into the architecture from Day 1 — it is a consequence of ISR entry overhead + context switch time + GPIO write, all of which are fixed by your task structure and clock config. If any driver (especially the I2C blocking transaction) or any ISR mask inadvertently disables preemption, the budget is silently violated and you won't know until Week 10 — with no time to fix it. On Cortex-M55 at 600 MHz, 1 ms = 600,000 cycles. That sounds like a lot until you realize a blocking I2C transaction for VL53L1X ranging takes 20 ms.
Resource: reference repo
The reference repo uses a semaphore-signaled ISR pattern (isp_sem) where the high-priority ISR simply signals a semaphore rather than doing any work inline. The actual processing happens in the high-priority task that wakes from that signal. Copy this pattern: your "Hazard Alert" Priority 1 task waits on a semaphore; the inference task signals it when a collision vector is predicted. The ISR itself is sub-microsecond.
Remaining action
Instrument with DWT cycle counter from first boot. Toggle a debug GPIO at ISR entry and at haptic GPIO set. Measure this with a logic analyzer or oscilloscope on Day 1 of sensor integration, not Week 10. Never make a blocking HAL call inside a high-priority task or ISR. All I2C transactions must live exclusively in the Priority 3 Sensor Acquisition Task.
Critical Shared inference result buffer between Priority 1 and Priority 2 tasks — race condition
The Priority 2 TinyML Inference Task writes a collision prediction result. The Priority 1 Hazard Alert Task reads it. If Priority 1 preempts Priority 2 mid-write, the read gets a half-updated, corrupted value. This is a classic RTOS race condition. In safety-critical systems, a corrupted false-negative (missed hazard) or false-positive (phantom alert) both cause failures. This bug is silent under normal operation and only manifests intermittently under timing stress — exactly the scenario of Week 14 outdoor field testing.
Resource: reference repo
The reference repo solves this with a buffer queue pattern using paired semaphores (bq->free and bq->ready) that enforce producer-consumer ordering with zero shared-memory race conditions. The producer (inference thread) only writes to a buffer when bq->free is available. The consumer (display/postprocess thread) only reads when bq->ready is signaled. Adapt this exact pattern for your inference result: inference task writes to a result slot and signals a semaphore; hazard task consumes only after the signal. The code is in app.c lines 280–330.
High VL53L1X + MPU6050 on shared I2C bus — blocking transactions will break the scheduler
VL53L1X ranging takes 20–100 ms per measurement in blocking mode. MPU6050 read is fast (~1 ms) but still blocks. If either I2C transaction runs inside a high-priority task (or worse, an ISR), it stalls the scheduler and destroys your real-time budget. Additionally, both devices share PB6/PB7 — bus arbitration must be managed, and pull-up resistors must be correct for 400 kHz fast mode (4.7 kΩ to 3.3V). Neither is mentioned in the plan.
Resource: reference repo
The reference repo uses DMA-based camera transfers and a dedicated ISP thread (Priority 10, highest) that handles all hardware I/O independently. Adapt this: put all I2C transactions in a dedicated Priority 3 Sensor Acquisition Task that runs on a hardware timer tick. Never call HAL_I2C_Master_Transmit with blocking timeout from any other task context.
Remaining action — hardware
Verify: 4.7 kΩ pull-ups to 3.3V on both SDA and SCL. VL53L1X XSHUT pin must be driven high to enable the sensor — if left floating the device is off and I2C returns NAK. Set VL53L1X timing budget to 20 ms minimum (API call: VL53L1X_SetTimingBudgetInMs(20)). Configure I2C in DMA mode, not polling. Confirm no address collision: VL53L1X = 0x29 (7-bit), MPU6050 = 0x68 or 0x69 depending on AD0 pin.
Medium SLEEP vs STOP mode — deep sleep conflicts with sub-ms interrupt wake requirement
The plan claims "deep sleep between polling intervals." On STM32N6, Stop mode wake-up requires HSE/HSI oscillator restart (5–50 µs). If an interrupt (collision ISR) fires during that restart window, response latency spikes unpredictably. For a < 1 ms preemption guarantee, Stop mode is incompatible with the safety-critical path.
Fix
Use WFI (Wait For Interrupt) SLEEP mode for the idle task — zero wake latency, modest power saving. Reserve Stop/Standby for an explicit "system off" state triggered by a long idle timeout (e.g. > 30 seconds with no detected motion from MPU6050). Measure actual idle current in WFI sleep mode first before claiming battery life specs.

Hardware & power
Critical ERM motors driven directly from STM32 GPIO — will permanently damage the SoC
The hardware diagram shows "PWM Signal (PA0)" going directly to ERM haptic motors. STM32N6 GPIO maximum source current is 25 mA per pin. ERM vibration motors draw 60–150 mA at 3V. Driving an ERM directly from GPIO will either fail to spin (insufficient current) or destroy the GPIO driver permanently (overcurrent). This is not a software issue — it will cause irreversible hardware damage the first time you power it on with a real motor. The reference repo uses no actuators, so it does not model this risk.
Fix — mandatory before any assembly
Two options. Option A (purpose-built, recommended): DRV2605L haptic driver IC. I2C-controlled, supports ERM and LRA motors, has a built-in waveform library, 1.8–5.5V supply, max 300 mA output. Connects to your existing I2C bus (address 0x5A). GPIO controls only the EN pin. Option B (discrete, simpler): NPN transistor (2N2222 or BC547) per motor. GPIO → 1 kΩ base resistor → transistor base. Motor connects collector to 5V rail (through transistor), emitter to GND. Add 1N4007 flyback diode across the motor (cathode to 5V, anode to collector). Each option costs under ₹50 per motor channel. This fix must happen before Week 11 assembly.
High Power budget uncalculated — Li-Po battery sizing is a guess
Battery is listed as "Li-Po" with no capacity, voltage, or runtime target. STM32N6 active at 600 MHz draws ~200–400 mA. VL53L1X ranging mode: 19 mA. MPU6050: 3.9 mA. Multiple ERM motors (peak): 60–150 mA each. Total peak: easily 500–700 mA. Without a power budget, a "4-hour wearable" claim is fabricated. The power stress test is in Week 13 — far too late to discover the system runs 20 minutes and requires a complete redesign.
Fix — calculate now
Power budget (rough): STM32N6 average (with NPU, periodic sleep) ~150 mA. VL53L1X continuous ranging: 19 mA. MPU6050: 4 mA. 2× ERM motors average duty (20% on-time): ~30 mA. Regulator overhead (3.3V LDO ~85% efficiency): +15%. Total average: ~235 mA. For 4-hour runtime: 235 mA × 4 h / 0.8 (Li-Po usable capacity) = 1,175 mAh minimum cell. Order a 1,500 mAh 3.7V Li-Po with a 3.3V regulator. Note: the STM32N6570-DK eval board is not power-optimized for wearable use — the final wearable power circuit is a separate hardware design task.
Medium Application executes from XSPI RAM — cache maintenance is mandatory for NPU correctness
The STM32N6 runs your application from XSPI external RAM. The Cortex-M55 has L1 I/D-Cache. When the NPU DMA reads model weights or writes inference outputs, it bypasses the CPU cache — meaning the CPU may read stale cached values from a region the NPU has already updated. This produces incorrect inference results with no error flag. The NeuralART compiler flag --cache-maintenance (visible in the reference repo's user_neuralart.json) enables automatic cache invalidation, but only for NPU-managed buffers. Your sensor input buffer (filled by I2C DMA) also needs explicit cache invalidation before the NPU reads it.
Resource: reference repo
The reference repo's user_neuralart.json already includes --cache-maintenance. Copy this config flag exactly. For your I2C sensor buffer: call SCB_InvalidateDCache_by_Addr() on the sensor input buffer after DMA completion and before triggering NPU inference. The reference repo's camera DMA pipeline does this for frame buffers — same pattern applies to your sensor data buffer.
